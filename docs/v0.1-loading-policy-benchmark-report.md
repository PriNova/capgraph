# V0.1 Graph Loading-Policy Benchmark Report

## 1. Result

The V0.1 loading-policy pilot completed all 18 scheduled runs:

- Flat: 6/6 independently verified success.
- Graph Progressive: 6/6 independently verified success.
- Graph Batch: 6/6 independently verified success.
- All Graph runs followed their required loading protocol.
- No task, protocol, tool, infrastructure, or independent-verification failures occurred.
- Every condition ultimately loaded the same five skill bodies.

Graph Batch removed much of the mechanical overhead measured in Graph Progressive. Compared with Graph Progressive, Batch reduced median graph load calls from five to one, tool calls from 10 to 6, turns from 8 to 7, duration by 17.5%, input tokens by 12.0%, output tokens by 38.0%, and cost by 17.5%.

Compared with Flat, Graph Batch used fewer turns, tool calls, output tokens, cache-read tokens, and wall-clock duration. Flat still used 28.5% fewer median input tokens than Batch and had 8.3% lower median cost. Both loaded all five bodies and achieved identical success.

The result supports a narrow conclusion:

> One-skill-at-a-time Graph loading caused a substantial part of V0's mechanical overhead. Batch loading removed most interaction overhead, but this shallow workflow still showed no reliability gain or reduction in loaded skill bodies. Flat remained slightly cheaper, while Graph Batch completed with fewer agent operations and lower duration.

This pilot has six runs per condition. It does not establish statistical significance.

## 2. Research Questions

### How much Graph overhead came from progressive loading?

A meaningful part of it. Graph Batch and Graph Progressive used the same metadata, bodies, closure, model, task, and execution interface. Replacing five individual graph loads with one batch load produced lower medians across turns, tool calls, duration, provider token usage, cache reads, and cost.

### Does Graph structure show value after removing root-prose composition leakage?

Only limited value in this task. Graph supplied deterministic composition with less returned capability-context payload than Flat, and Batch required fewer agent operations. However, all conditions still loaded the same five bodies and all succeeded. Flat retained lower input-token usage and cost than Batch.

The simple physics-object workflow remains too small and shallow to test whether Graph can avoid irrelevant capability prose in a larger library.

## 5. Composition-Leak Control

The `physics-object-create` body was changed before V0.1. It now describes capability purpose, inputs, output, execution semantics, root-specific caveats, and completion criteria without naming or listing its dependencies or verifier.

CapGraph metadata remained the composition source of truth:

```yaml
capgraph-requires: "object-create rigid-body-add collision-add"
capgraph-verify-with: "physics-object-verify"
```

Automated tests confirmed:

- Flat fixture generation removed CapGraph metadata;
- Flat and Graph Markdown bodies were content-identical;
- the composite root body did not repeat related skill names or the dependency sequence.

Graph prose was not richer than Flat prose.

## 6. Conditions

### Flat

- All five skill names and descriptions were present through normal skill discovery.
- Full generated `SKILL.md` files were loaded with `read`.
- Graph metadata and `skill_graph` were unavailable.

### Graph Progressive

- No flat skill catalog was present.
- `expand` returned metadata only.
- The agent loaded bodies through individual `load(skill)` calls.
- `load_many` was prohibited by the benchmark protocol.

### Graph Batch

- No flat skill catalog was present.
- `expand` returned the same metadata as Graph Progressive.
- One `load_many(root)` call returned the deterministic execution closure and verifier body.
- Execution and verification bodies remained structurally separate in the result.
- Individual graph loads and eager recovery loading were prohibited.

All conditions used identical Markdown bodies and the same UPBGE operations.

## 12. Observed Operation Sequences

Every condition loaded all five bodies:

1. `object-create`
2. `rigid-body-add`
3. `collision-add`
4. `physics-object-create`
5. `physics-object-verify`

Flat loaded the root and four related files before mutation. Some reads completed in parallel, so recorded completion order varied.

Every Graph Progressive run used:

```text
expand root
load root
load object-create
load rigid-body-add
load collision-add
load physics-object-verify
create cube
add rigid body
add collision
verify
```

Every Graph Batch run used:

```text
expand root
load_many root closure
create cube
add rigid body
add collision
verify
```

All conditions used the same mutation and verification order:

```text
create_cube
add_rigid_body
add_collision
verify_physics_object
```

Three Flat runs and one Graph Progressive run also called the non-mutating UPBGE `status` operation. No Graph Batch run called it. This model-selected variation accounts for some tool-count variation and is not a loading-policy requirement.

## 14. Interpretation

### Progressive interaction overhead

The direct Progressive-to-Batch comparison isolates loading policy more cleanly than either Graph-to-Flat comparison. Both Graph conditions received identical metadata and bodies. The primary controlled difference was five individual loads versus one batch load.

Batch improved every measured median provider and interaction metric relative to Progressive except returned capability-context bytes, which increased by 0.9% because of serialization structure. This indicates that repeated graph interactions and context replay caused a substantial part of Progressive's overhead.

### Graph versus Flat after leak removal

Removing dependency names and workflow sequence from the root did not cause a success difference. Flat still selected and loaded all five relevant bodies from a five-skill catalog. Graph also loaded all five bodies.

Graph Batch provided deterministic composition with fewer agent operations and lower duration than Flat. However, it did not reduce loaded body count, and provider input usage and cost remained higher. The tested workflow therefore does not demonstrate an overall Graph efficiency or reliability advantage.

### Practical decision

For future Graph composition benchmarks, Batch is the better default loading policy than one-skill-at-a-time Progressive loading. This is a benchmark-policy decision, not evidence that Graph is generally better than Flat.

The next composition benchmark must test a larger catalog with transitive and shared dependencies, irrelevant skills, verifier ambiguity, and one controlled recovery path. Its graph closure should be materially smaller than the available library.

## 15. Limitations

- Six samples per condition are too few for statistical significance.
- Only one task and one model configuration were tested.
- The capability library contained only five skills.
- The workflow had shallow direct dependencies.
- Every condition loaded every available body.
- No optional branch or recovery path was exercised.
- The known root removed intent-resolution difficulty.
- Model-selected `status` calls varied across conditions.
- Wall-clock duration includes provider and local runtime variability.
- Byte categories do not provide exact provider token attribution.
- Automatic reset removed only the reserved object and its unused mesh; it did not reload a complete scene fixture.

## 16. Decision

Use Graph Batch, not Graph Progressive, as the graph loading policy for the planned V1 composition benchmark.

Do not claim that Graph Batch beat Flat overall. In V0.1:

- reliability was equal;
- Batch minimized agent operations and duration;
- Flat minimized provider input and cost;
- neither avoided any skill body.

Proceed to V1 only to test conditions where graph structure can plausibly reduce exploration or irrelevant prose. Do not add intent resolution, semantic search, databases, caching infrastructure, self-learning, or graph mutation.
